# Task
[llm_memory_design_v5.md](llm_memory_design_v5.md) 是当前记忆系统的算法介绍，当前目录（`ZDMem`）则包含该系统源码。

你的目的则是要考虑优化这个系统，主要从记忆更新抽取和检索2大部分优化。

# 优化思路
直接看源码固然是一种方法，但是难度较大，缺乏高质量的测试数据注定无法保证优化效果。

因此本次优化使用locomo测试集，通过对badcase的分析来进行优化

## Locomo数据集介绍
Locomo数据主要包括2部分：
1. 2个人之间的多段对话（发生在不同的时间点），该数据一共有10对人的多段对话
2. 针对所有对话的相关的QA

## Locmo数据集目录介绍
数据集已经处理好，在`ZDMem/scripts/evaluate_locomo/processed_locomo_test_data`中
该目录共有10个子目录分别代表2个人之间的多段对话，比如`1__Jon__Gina`就代表Jon 和 Gina之间的多段对话。
每个子目录下，会有`session_*.txt`代表一段对话，还有`test_qa.json`代表针对这2个人的所有的对话的qa测试集

## 使用Locomo数据集优化记忆系统
我们使用类似于RAG的方法进行测试：
Step1, 记忆获取，对于每一对人，从他们的所有对话中抽取相关记忆，这里就要使用我们的记忆系统
Step2, 预测答案，对于qa数据中的每一个q，搜索相关的记忆，然后让LLM基于记忆回答问题
Step3, 评估效果，LLM as Judge, 给定LLM正确答案和预测答案，判断预测答案是否正确
Step4, 优化系统，认真分析错误的预测，尝试进行优化

## 执行说明
执行代码位于`ZDMem/scripts/evaluate_locomo`目录下。

Step1参考示例代码`ZDMem/examples/example_usage.py`，核心是使用`process_memories`抽取记忆，使用`hybrid_search`搜索记忆。

Step2和Step3需要自行编写prompt完成。

test_qa.json中的evidence字段（如"D1:2"表示session_1.txt中dialogue_id为D1:2的对话）可作为参考信息，也可用于辅助判断记忆是否覆盖了关键信息。

## Badcase分析
分析结果保存在`ZDMem/scripts/evaluate_locomo/badcase_analysis/`目录下，格式自行决定，保证可读性即可。

分析时需要区分问题来源：
- 记忆抽取问题：关键信息未被抽取为记忆
- 记忆检索问题：记忆存在但未被检索到
- 其他问题：如问题本身过难、需要复杂推理等

## 优化产出
优化产出为分析报告和建议，由人工审核后再决定是否修改代码。

## 测试数量
测试集数量较多，优化约100条badcase即可，无需追求全部覆盖。

FAQ:
Q1: Locomo数据集的对话并不长，为什么不把整段对话放进去，然后根据q预测答案呢？这样一定不会丢失任何信息！
A1: 是的，这样效果反而更好，但是我们使用locomo的目的是来优化记忆系统的，我们并不是为了追求更高测试分数

Q2: 为啥非要抽取记忆？直接把对话切成chunk，然后走常规RAG不行吗？
A2: 可以，当然可以，但是如上所述，我们的目的是为了优化记忆系统，所以不会考虑其他方法

Q3: Q1和Q2都可以回答问题，为啥非得要记忆系统？有这个必要吗？
A3: 非常有必要，如果对话非常长，是近2年来的对话，长度可达千万级别tokens, Q1的方法就会失效。Q2的chunk方法会丢失大量上下文信息，效果肯定不会好

# 注意事项
1. 避免针对性优化，要发现错误的本质原因！不要陷入过拟合陷阱，不要进行非常规优化
2. 接受不完美，有些QA难度过大，可能当前技术发展水平就是无法解决，那我们旧不解决
3. 主动给建议，对于一些无法优化bad case, 可以认真分析，给出一些系统建议
4. 优化范围，主要还是针对系统进行优化，如果需要对记忆系统架构进行修改才能解决，那么就不要优化，而是而出建议，让我自行判断
